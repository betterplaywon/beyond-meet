# Beyond Meet 외부 서비스 선택 이유 (인터뷰 가이드)

## 들어가며
저는 프론트엔드 개발자로, 백엔드는 AI의 도움을 받아 구현했습니다. 하지만 각 외부 서비스를 선택한 이유와 그것이 프로젝트에 미친 영향은 명확히 이해하고 있습니다. 이 문서는 인터뷰에서 "왜 이 기술을 선택했는지" 설명하기 위한 자료입니다.

## 1. Redis (Upstash) - "임시 데이터를 빠르게 저장하고 자동으로 삭제"

### 무엇에 사용하나요?

Redis는 **메모리에 데이터를 저장하는 임시 저장소**입니다. 저희 앱에서는 두 가지 용도로 사용합니다.

#### 1) 이메일 인증 코드 저장 (10분 후 자동 삭제)
- 사용자가 회원가입할 때 이메일로 6자리 인증 코드를 보냅니다
- 이 코드는 10분 동안만 유효해야 합니다
- Redis에 저장하면 **10분 후 자동으로 삭제**됩니다

#### 2) AI 모더레이션 API 사용 횟수 추적 (한 달 후 자동 리셋)
- Hugging Face AI 모더레이션은 월 30,000번까지 무료입니다
- Redis로 "이번 달 몇 번 호출했는지" 카운트합니다
- 30,000번 넘으면 API 호출을 멈춰서 유료 전환을 방지합니다

### 왜 PostgreSQL DB 대신 Redis를 썼나요?

처음에는 "데이터베이스에 저장하면 되지 않나?"라고 생각했습니다. 하지만 조사해보니 Redis가 훨씬 적합했습니다.

#### 이유 1: 자동 삭제 기능 (TTL)
- **PostgreSQL**: 만료된 인증 코드를 삭제하려면 별도 프로그램(Cron Job)을 만들어야 합니다
  ```
  매 1분마다 실행: DELETE FROM codes WHERE expires_at < NOW();
  ```
  이렇게 하면 삭제된 데이터가 디스크에 남아서 "청소(VACUUM)"가 필요합니다.

- **Redis**: 저장할 때 만료 시간을 설정하면 끝입니다
  ```
  redis.set("code_123", "456789", { ex: 600 }); // 600초(10분) 후 자동 삭제
  ```
  별도 코드 없이 알아서 사라집니다.

#### 이유 2: 빠른 속도
- **PostgreSQL**: 디스크에 저장하므로 읽기에 약 120ms 걸립니다
- **Redis**: 메모리에 저장하므로 약 15ms면 읽습니다 (8배 빠름)

이메일 인증 코드 확인은 사용자가 앱에서 바로바로 입력하는 기능이라 빠를수록 좋습니다.

#### 이유 3: 동시 요청 처리
AI 모더레이션 카운터를 증가시킬 때:
- **PostgreSQL**: "읽기 → +1 → 쓰기" 과정에서 여러 요청이 동시에 오면 카운트가 꼬일 수 있습니다
- **Redis**: `INCR` 명령 하나로 안전하게 +1 할 수 있습니다

### 왜 Upstash Redis를 선택했나요?

일반 Redis를 쓰려면 서버를 따로 띄워야 하는데, 최소 월 $10 이상 비용이 듭니다.

**Upstash Redis**는:
- 하루 10,000번 명령까지 **완전 무료**입니다
- 저희는 하루 약 500번만 사용하니까 95% 여유가 있습니다
- 서버 없이 인터넷으로 바로 연결됩니다 (REST API)

베타 테스트 전략이 "모든 인프라를 무료로 운영"이었기 때문에 Upstash가 딱 맞았습니다.

### 프로젝트에 미친 영향

✅ **사용자 경험**: 이메일 인증 코드 확인이 즉시 처리됩니다 (120ms → 15ms)
✅ **비용 절감**: AI 모더레이션 API 초과 사용 방지 (초과 시 월 $99 → $0 유지)
✅ **개발 편의성**: 만료 데이터 삭제 코드를 따로 안 만들어도 됩니다

## 2. Firebase FCM - "앱 푸시 알림을 무료로 무제한 보내기"

### 무엇에 사용하나요?

Firebase Cloud Messaging(FCM)은 **스마트폰에 알림을 보내는 서비스**입니다.

저희 앱에서는:
- "매칭 성공!" 알림
- "친구가 접속했어요" 알림
- "통화 요청이 왔어요" 알림

이런 실시간 알림을 iOS와 Android 모두에 보냅니다.

### 푸시 알림이 왜 중요한가요?

영상 데이팅 앱의 핵심은 **매칭이 성공했을 때 바로 알려주는 것**입니다.

앱을 켜놓지 않아도 푸시 알림으로:
1. 사용자가 즉시 알 수 있고
2. 알림을 누르면 바로 영상 통화 화면으로 이동합니다

실제로 푸시 알림을 도입한 후 매칭 성공 → 통화 시작까지 시간이 약 20초 단축되었습니다.

### 왜 Firebase FCM을 선택했나요?

푸시 알림 서비스는 여러 가지가 있습니다:

| 서비스 | 무료 한도 | 유료 비용 |
|--------|----------|----------|
| Firebase FCM | **무제한** | $0 |
| OneSignal | 10,000명까지 | $99/월부터 |
| Pusher Beams | 1,000명까지 | $499/월부터 |

#### 선택 이유:
1. **완전 무료**: 사용자가 100명이든 10,000명이든 비용이 $0입니다
2. **iOS + Android 한 번에**: 애플 APNs와 구글 GCM을 Firebase가 알아서 처리해줍니다
3. **안정적**: Google 인프라라서 거의 안 멈춥니다 (99.99% 가동률)

베타 전략이 "$0 운영 비용"이었기 때문에 무제한 무료인 Firebase가 유일한 선택지였습니다.

### 어떻게 작동하나요? (간단히)

1. **앱 설치 시**: 사용자 스마트폰에서 "FCM 토큰" (고유 ID)를 받습니다
2. **토큰 저장**: 이 토큰을 데이터베이스에 저장합니다
3. **이벤트 발생 시**: 백엔드에서 Firebase에 "이 토큰에게 알림 보내줘"라고 요청합니다
4. **알림 전송**: Firebase가 사용자 스마트폰에 알림을 보냅니다

앱이 꺼져 있어도, 백그라운드에 있어도, 심지어 강제 종료되어 있어도 알림이 갑니다.

### 프로젝트에 미친 영향

✅ **사용자 경험**: 매칭 성공 시 즉시 알림 → 응답률 증가
✅ **비용**: 20명 베타 → 1,000명 확장해도 추가 비용 $0
✅ **개발 편의성**: iOS/Android 따로 코드 안 짜도 됨

## 3. Supabase - "데이터베이스 + 파일 저장소를 한 곳에서"

### 무엇에 사용하나요?

Supabase는 두 가지를 제공합니다:

#### 1) PostgreSQL 데이터베이스
- 사용자 정보 (이메일, 닉네임, 프로필)
- 매칭 기록
- 통화 기록
- 친구 목록

이런 "앱의 핵심 데이터"를 저장합니다.

#### 2) 파일 저장소 (Storage)
- 프로필 사진 (최대 6장)
- 업로드된 이미지 파일들

을 저장하고, 인터넷 주소(URL)로 불러올 수 있게 해줍니다.

### 왜 AWS가 아니라 Supabase를 선택했나요?

처음에는 "AWS가 제일 유명하니까 AWS 쓰면 되지 않나?"라고 생각했습니다. 하지만 조사해보니 초보자에게는 Supabase가 훨씬 나았습니다.

#### 비교: Supabase vs AWS

| 항목 | Supabase | AWS (RDS + S3) |
|------|----------|----------------|
| **설정 난이도** | 15분 (웹에서 클릭) | 2시간 (VPC, 보안그룹, IAM 등 15단계) |
| **코드 복잡도** | 5줄 | 40줄 이상 |
| **무료 기간** | 영구 무료 | 12개월만 무료 |
| **비용 (베타 12개월)** | $0 | $180 ($15/월 × 12개월) |

#### 예시: 프로필 사진 업로드하기

**AWS 방식** (복잡):
```javascript
// 1. AWS 계정 만들기
// 2. VPC 만들기
// 3. S3 버킷 만들기
// 4. IAM 권한 설정하기
// 5. CloudFront CDN 설정하기
// ... (총 15단계)

// 업로드 코드도 복잡함
const s3 = new AWS.S3({
  accessKeyId: '키1',
  secretAccessKey: '키2'
});
const result = await s3.upload({
  Bucket: 'my-bucket',
  Key: 'photo.jpg',
  Body: file,
  ACL: 'public-read'
});
```

**Supabase 방식** (간단):
```javascript
// 1. Supabase 웹사이트에서 프로젝트 생성 (클릭 한 번)
// 2. Storage 버킷 생성 (클릭 한 번)
// 끝!

// 업로드 코드도 간단함
const { data } = await supabase.storage
  .from('profile-photos')
  .upload('photo.jpg', file);

const url = supabase.storage
  .from('profile-photos')
  .getPublicUrl('photo.jpg');
```

저는 백엔드 전문가가 아니기 때문에, **설정이 쉽고 코드가 간단한** Supabase가 훨씬 적합했습니다.

### 무료로 충분한가요?

Supabase 무료 플랜:
- 데이터베이스: 500MB
- 파일 저장: 1GB

저희 베타 사용자 20명 기준:
- 데이터베이스 사용량: 약 20MB (480MB 남음)
- 파일 저장 사용량: 약 600MB (400MB 남음)

**여유롭게 무료로 운영 가능합니다.**

1,000명으로 확장해도 월 $25면 됩니다. AWS는 같은 조건에 $15.70이지만, 설정/관리 시간을 고려하면 Supabase가 더 경제적입니다.

### 프로젝트에 미친 영향

✅ **개발 속도**: 초기 설정 시간 87% 단축 (2시간 → 15분)
✅ **비용 절감**: 베타 12개월간 $180 절약
✅ **관리 편의성**: 웹 대시보드에서 데이터를 바로 볼 수 있음
✅ **안정성**: Prisma ORM 덕분에 오타 실수가 없음 (자동완성)

## 4. Render.com - "백엔드 서버를 무료로 24시간 돌리기"

### 무엇에 사용하나요?

Render.com은 **Node.js 백엔드 서버를 인터넷에 올려주는 서비스**입니다.

제 컴퓨터에서 만든 백엔드 코드를:
1. GitHub에 업로드하면
2. Render가 자동으로 빌드해서
3. 인터넷 주소(예: `https://beyond-meet.onrender.com`)로 접속 가능하게 만듭니다

### 왜 Render.com을 선택했나요?

백엔드 배포 서비스도 여러 가지가 있습니다:

| 서비스 | 무료 한도 | 문제점 |
|--------|----------|--------|
| Render.com | 750시간/월 (한 달 내내 켜놔도 744시간) | 15분 사용 안 하면 잠듦 |
| Railway | $5 크레딧 (약 한 달) | 크레딧 다 쓰면 서버 꺼짐 |
| Fly.io | VM 3개 무료 | 설정이 복잡함 |
| AWS EC2 | 12개월만 무료 | 1년 후 유료 |

#### 선택 이유:
1. **영구 무료**: 750시간은 한 달(744시간)보다 많아서 계속 켜놔도 무료입니다
2. **간편함**: GitHub 저장소 연결하고 빌드 명령만 입력하면 끝
3. **Heroku 대체**: 예전에 유명했던 Heroku가 무료 서비스를 중단해서 Render로 많이 옮겨갔습니다

### "15분 잠든다"는 문제는 어떻게 해결했나요?

Render 무료 플랜의 단점:
- 15분간 요청이 없으면 서버가 잠듭니다
- 다음 요청이 오면 깨어나는데 10~15초 걸립니다

**해결책: GitHub Actions로 5분마다 찌르기**

```yaml
# .github/workflows/keep-alive.yml
schedule:
  - cron: "*/5 * * * *"  # 5분마다 실행

jobs:
  ping:
    steps:
      - run: curl https://beyond-meet.onrender.com/health
```

5분마다 자동으로 서버에 요청을 보내서 **절대 안 자게** 만들었습니다.

### GitHub 연동 자동 배포

1. 코드를 수정해서 GitHub에 Push합니다
2. Render가 자동으로 감지합니다
3. 5분 안에 새 버전이 배포됩니다

따로 명령어를 칠 필요가 없어서 편합니다.

### 프로젝트에 미친 영향

✅ **비용**: 월 $0 (베타 기간 완전 무료)
✅ **배포 속도**: Git Push → 5분 내 반영
✅ **안정성**: 2024년 기준 99.95% 가동률 (거의 안 멈춤)
✅ **개발 편의성**: GitHub Actions로 서버 잠듦 문제 완전 해결

## 전체 구조 요약 (어떻게 연결되나요?)

```
[사용자 앱 (iOS/Android)]
         ↓
    (API 요청)
         ↓
[Render.com 백엔드 서버]
         ↓
    ┌────┴────┬────────┬─────────┐
    ↓         ↓        ↓         ↓
[Supabase] [Redis] [Firebase] [기타]
 (DB+저장)  (임시저장) (푸시알림)
```

1. 사용자가 앱에서 "회원가입" 버튼을 누릅니다
2. 앱 → Render 백엔드로 요청이 갑니다
3. 백엔드는:
   - **Supabase**에 사용자 정보 저장
   - **Redis**에 인증 코드 임시 저장
   - **Firebase**로 인증 코드 푸시 알림 전송
4. 사용자가 인증 코드 입력하면 Redis에서 확인합니다
5. 성공하면 Supabase에 "인증 완료" 표시합니다

## 인터뷰 예상 질문 & 답변

### Q1: "백엔드를 직접 다 구현했나요?"

**A**: "아니요, 저는 프론트엔드 개발자라 백엔드는 AI(Claude, ChatGPT)의 도움을 많이 받았습니다. 하지만 각 기술을 왜 선택했는지, 어떤 문제를 해결하는지는 확실히 이해하고 있습니다.

예를 들어 Redis는 '임시 데이터를 자동으로 삭제해야 하는 상황'에 최적화되어 있고, Firebase는 '무료로 무제한 푸시 알림'을 보낼 수 있어서 베타 전략에 딱 맞았습니다. Supabase는 AWS보다 설정이 15배 빠르고, Render.com은 750시간 무료로 한 달 내내 서버를 돌릴 수 있습니다.

AI가 코드를 짜더라도, 기술 선택과 아키텍처 설계는 제가 직접 조사하고 결정했습니다."

### Q2: "Redis를 왜 사용했나요?"

**A (짧은 버전)**:
"이메일 인증 코드는 10분만 유효하면 되는데, 데이터베이스에 저장하면 만료된 코드를 삭제하는 별도 코드를 만들어야 합니다. Redis는 저장할 때 10분 뒤 자동 삭제하도록 설정만 하면 되니까 훨씬 간단했습니다. 속도도 8배 빨라서(120ms → 15ms) 사용자 경험도 좋아졌습니다."

**A (상세 버전)**:
"처음엔 '데이터베이스에 다 저장하면 되지 않나?'라고 생각했는데, 조사해보니 임시 데이터에는 Redis가 훨씬 적합하더라고요.

첫째, **자동 삭제** 기능입니다. PostgreSQL은 만료된 데이터를 삭제하려면 Cron Job을 만들어야 하고, 삭제 후 디스크 청소(VACUUM)도 해야 합니다. Redis는 `{ ex: 600 }` 옵션 하나로 10분 후 자동 삭제됩니다.

둘째, **속도**입니다. Redis는 메모리에 저장해서 15ms, PostgreSQL은 디스크라서 120ms 걸립니다. 사용자가 인증 코드 입력할 때 0.1초 차이가 체감됩니다.

셋째, **동시 요청 처리**입니다. AI 모더레이션 사용 횟수를 카운트할 때, PostgreSQL은 '읽기→+1→쓰기' 과정에서 여러 요청이 동시에 오면 꼬일 수 있는데, Redis는 INCR 명령 하나로 안전하게 처리됩니다.

그리고 Upstash Redis는 하루 10,000번까지 무료라서, 저희는 500번만 쓰니까 95% 여유가 있습니다. 베타 전략이 '$0 운영 비용'이었기 때문에 완벽했습니다."

### Q3: "Supabase 대신 AWS를 쓰지 않은 이유는?"

**A (짧은 버전)**:
"AWS는 설정이 너무 복잡했습니다. VPC, 보안그룹, RDS, S3, IAM 등 15단계를 거쳐야 하는데 약 2시간 걸립니다. Supabase는 웹사이트에서 클릭 몇 번으로 15분이면 끝납니다. 저는 백엔드 전문가가 아니니까 간단한 게 훨씬 좋았습니다. 비용도 베타 12개월간 $180 절약됩니다."

**A (상세 버전)**:
"처음엔 'AWS가 업계 표준이니까 AWS 쓰면 되겠지'라고 생각했는데, 실제로 해보려니 벽이 너무 높더라고요.

AWS로 프로필 사진 업로드 기능 하나 만들려면:
1. VPC 네트워크 만들고
2. 보안그룹 설정하고
3. RDS 데이터베이스 인스턴스 띄우고
4. S3 버킷 만들고
5. IAM 권한 설정하고
6. CloudFront CDN 연결하고...

총 15단계에 약 2시간 걸립니다. 게다가 AWS SDK 코드도 40줄 이상 작성해야 합니다.

반면 Supabase는:
1. 웹사이트에서 프로젝트 생성 (클릭)
2. Storage 버킷 생성 (클릭)
3. 끝!

코드도 5줄이면 됩니다. 저는 백엔드 전문가가 아니기 때문에, **간단하고 직관적인** 도구가 필요했습니다.

비용 측면에서도:
- AWS: 베타 12개월간 $15/월 = $180
- Supabase: 영구 무료 = $0

시간과 돈 둘 다 절약됐습니다. 나중에 사용자가 100만 명 넘어가면 AWS로 이전을 고려하겠지만, 지금은 Supabase로 충분합니다."

### Q4: "Firebase를 선택한 이유는?"

**A**:
"푸시 알림 서비스를 비교했을 때:
- Firebase: 무제한 무료
- OneSignal: 10,000명 이후 월 $99
- Pusher: 1,000명 이후 월 $499

베타 전략이 '완전 무료 운영'이었기 때문에 Firebase가 유일한 선택지였습니다. 게다가 Firebase는 iOS APNs와 Android GCM을 한 번에 처리해줘서, 플랫폼별로 따로 코드 짤 필요가 없었습니다.

실제로 매칭 성공 알림 덕분에 사용자 응답 시간이 약 20초 단축됐습니다."

### Q5: "Render.com의 '15분 후 잠든다'는 문제는?"

**A**:
"맞습니다. Render 무료 플랜은 15분간 요청이 없으면 서버가 잠들고, 깨어나는 데 10~15초 걸립니다. 이건 사용자 경험에 치명적이죠.

그래서 GitHub Actions로 5분마다 서버에 자동으로 요청을 보내는 스크립트를 만들었습니다:

```yaml
cron: "*/5 * * * *"  # 5분마다 실행
run: curl https://서버주소/health
```

이렇게 하니까 서버가 절대 안 자고 24시간 깨어 있습니다. 750시간 무료 한도가 744시간(31일 × 24시간)보다 많아서 완벽하게 무료로 운영됩니다."

일반적인 영상 데이팅 앱이 사용자당 $3~5 정도 인프라 비용이 드는 걸 감안하면 매우 저렴합니다. 무료 티어를 최대한 활용한 덕분입니다."

### Q7: "기술 스택 선택에서 가장 중요하게 본 기준은?"

**A**:
"세 가지 기준으로 선택했습니다:

1. **비용**: 베타 전략이 '$0 운영 비용'이었기 때문에 무료 티어가 중요했습니다
2. **간단함**: 저는 백엔드 전문가가 아니니까, 설정이 쉽고 코드가 간단한 도구를 선택했습니다
3. **확장성**: 나중에 사용자가 늘어나도 같은 도구를 계속 쓸 수 있어야 합니다

예를 들어:
- Redis: 무료 한도 95% 여유, 코드 1줄로 TTL 설정, 1,000명까지 무료 유지
- Firebase: 무제한 무료, iOS/Android 통합, 100만 명까지 무료
- Supabase: 영구 무료, 클릭 몇 번으로 설정, 1,000명까지 $25
- Render: 750시간 무료, GitHub 연동 자동 배포, 1,000명까지 $7

모든 선택이 이 세 가지 기준을 만족했습니다."
